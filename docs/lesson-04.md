# Lesson 04 — Settlement: จ่ายเงินจริงบน Stripe Checkout (Test Mode)

![stripe payment demo](media/lesson-04/demo.gif)

## Goal
เห็นว่า "settlement" (การเคลื่อนเงินจริง) เกิดขึ้นที่ Stripe ทั้งหมด ไม่ใช่ที่ backend ของเรา — backend มีหน้าที่แค่ **ร้องขอ** ให้เกิดการจ่ายเงิน แล้วรอฟังผลใน [lesson 05](lesson-05.md)

## สิ่งที่ทำ
คลิก "ซื้อเลย" แล้วเบราว์เซอร์ถูก redirect ไปหน้า Stripe Checkout ที่ host โดย Stripe เอง (`checkout.stripe.com`) — เราไม่เคยเห็นเลขบัตรเครดิตของลูกค้าเลยแม้แต่ตัวเดียว กรอกบัตรทดสอบมาตรฐานของ Stripe (`4242 4242 4242 4242`) แล้วกด Pay สำเร็จจริงใน sandbox

## ทำไม redirect ไป Stripe แทนที่จะรับเลขบัตรเอง
| แบบ | ข้อดี | ข้อเสีย |
|---|---|---|
| **Stripe Checkout (redirect, ที่เลือกใช้)** | ไม่ต้องยุ่งกับ PCI-DSS compliance เลย เพราะเลขบัตรไม่ผ่าน server เรา, ได้ UI ที่ Stripe ทดสอบมาแล้วว่า convert ดี | คุม UI หน้าจ่ายเงินเองไม่ได้เต็มที่ |
| **Stripe Elements (embed ในหน้าเรา)** | UI ต่อเนื่อง ไม่ redirect ออก | ต้องทำ PCI compliance บางส่วน, โค้ด frontend ซับซ้อนขึ้นมาก |
| **รับเลขบัตรเอง แล้วส่งต่อ Stripe** | — | **ห้ามทำ** เกือบทุกกรณี ผิด PCI-DSS ตรง ๆ |

สำหรับ workshop ที่เน้น agentic checkout, Checkout Session ยังมีข้อดีอีกอย่าง: agent (lesson 06) ส่งแค่ "ลิงก์" ให้ผู้ใช้ ไม่ต้องจับลอจิกฟอร์มจ่ายเงินใด ๆ เลย — ความรับผิดชอบเรื่องเงินอยู่ที่ Stripe ล้วน ๆ

## สถานะหลังจ่ายเงิน: ทำไมหน้า success ยังบอก "pending"
สังเกตว่า frame แรกหลังจ่ายเงินสำเร็จ หน้า `/success` จะขึ้น "กำลังรอ Stripe ยืนยัน webhook..." ไม่ใช่ "จ่ายสำเร็จ" ทันที — เพราะ **การ redirect กลับมาไม่ได้แปลว่าเงินเข้าแล้วเสมอไป** (เช่น PromptPay/บัตรบางประเภทอนุมัติแบบ async) ระบบนี้เลยแยก "ผู้ใช้เห็นอะไร" ออกจาก "เราเชื่อว่าจ่ายจริงหรือยัง" อย่างชัดเจน ซึ่งเป็นประเด็นหลักของ lesson ถัดไป

## ต่อยอดได้อะไร
- เปิดใช้ PromptPay ใน Checkout Session (ปัจจุบัน UI Stripe แสดงให้เลือกอยู่แล้วเพราะ currency เป็น THB) แล้วสังเกตความต่างของ async flow
- ลองทำบัตรที่ตั้งใจให้ fail (`4000 0000 0000 0002`) เพื่อดู error handling
